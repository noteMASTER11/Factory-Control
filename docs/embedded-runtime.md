# Единый процесс приложения

Публикуется один файл: `dist/FactoryControl.exe`, примерно 199 МиБ. Внутри — Bridge, Gateway, управляемая часть .NET, нативные DLL, HTML/CSS/JS, звуки, шрифты и изображения. Рядом не нужны Web, DLL или конфигурация служб. Установленный WebView2 Runtime используется как прежде.

Стандартный .NET single-file включает нативные библиотеки с извлечением при первом запуске. Встроенный архив Web извлекается по хешу в `D:/ChatGPT/Cache/FactorioMonitor/Web`. Нативный apphost получает маленькую стартовую секцию до инициализации .NET: она задаёт process-scoped `DOTNET_BUNDLE_EXTRACT_BASE_DIR=D:/ChatGPT/Cache/FactorioMonitor/Bundle` и TEMP/TMP на D:. Стек и регистры восстанавливаются перед штатной точкой входа; исходная таблица CFG сохраняется и дополняется новой точкой входа. Это тот же процесс, без bootstrap EXE и дочерних Bridge/Gateway. Публикация воспроизводится `scripts/build.ps1 -Publish`; секция добавляется `scripts/patch-bundle-entry.py` только к собственной неподписанной сборке. Механизм .NET описан в [документации Microsoft](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/).

`App` сразу показывает окно и параллельно запускает `DesktopBackend` в фоновом потоке. Сначала запускается мост, затем шлюз. Окно ожидает готовности служб асинхронно перед первым запросом. У каждого host собственные DI-контейнер, кеш и курсор обновлений. В монолитной сборке `ITelemetrySource` передаёт ссылки на неизменяемые готовые снимки; внутренней MCP/HTTP-сериализации больших данных нет. При раздельном запуске Gateway сохраняет фиксированный MCP-клиент. ИИ не нужен.

Маршруты сохранены: мост `127.0.0.1:18740/mcp`, API `127.0.0.1:18741/api/v1/*`. `/health` обоих компонентов сообщает `process_id` основного приложения и `hosting=desktop`. Метаданные файлов проверяются раз в 250 мс, разбор изменённых файлов ограничен интервалами каналов 1–15 секунд (`TelemetryCadence`). Полные подробности запросов остаются в валидированном UTF-8, сводка считается один раз на поколение страниц; публичные маршруты выдают обычный JSON с полными данными. Запросы интерфейса читают кеш и SQLite, обходов игры не запускают.

Новые записи истории сохраняются как Brotli BLOB с быстрым сжатием; чтение старого JSON TEXT поддерживается. Индексы по времени и сессии позволяют чистить/читать историю без полного прохода многогигабайтных строк. Уже существующий файл SQLite автоматически не уплотняется; размер файла может отражать ранее выделенные страницы.

Наблюдение за игровой сессией также встроено в приложение: Windows WMI раз в две секунды читает PID, путь и командную строку Factorio. Привязка обновляется атомарно только при единственном подходящем процессе и изменении PID/времени создания. Профили с `--config`, headless-серверы и benchmark исключены. Проверка пути/времени создания в Bridge сохранена. PowerShell-наблюдатель при обычном запуске больше не нужен.

Профиль читается из `Data/LiveGame/profile.json`; история остаётся в `Data/history.db`. Для проверочной копии есть явные `--data-root`, `--telemetry-directory`, `--source-kind=validation_copy`. При явном каталоге телеметрии автоматическая перепривязка к основной игре отключена. Повторный запуск блокируется именованным mutex. При закрытии сначала завершается клиент шлюза, затем мост; оба порта освобождаются. Ошибка старта записывается в `Data/logs/desktop-backend.log`. Сбой запуска шлюза также завершает уже запущенный мост.

`scripts/start-desktop.ps1` и совместимый `scripts/start.ps1` запускают только приложение. `scripts/stop.ps1` закрывает его окно и ждёт штатного завершения. `scripts/build.ps1 -Publish` собирает все библиотеки и публикует только единый Desktop EXE в dist. Старые опубликованные Bridge/Gateway и прежняя оболочка перенесены в `D:/ChatGPT/Temp/FactorioMonitor/unified-backend-*` при переходе.

Проверки `DesktopBackendTests` и `TelemetryPerformanceTests`: передача готовых снимков внутри процесса, отдельный MCP-сценарий с полными подробностями, одинаковый PID, совместимость/сжатие SQLite, частота чтения, повторное занятие портов после завершения и завершение моста при конфликте порта шлюза. `TelemetryAllocationTests` ограничивает повторные выделения памяти при неизменном наборе страниц. `scripts/measure-desktop.ps1` измеряет CPU и память всей группы с WebView2. Проверка на текущей игре не меняет сохранение или игровой процесс.
